# ADR-0002：文件工具采用有界读取、唯一匹配和单文件原子替换

- 日期：2026-08-24
- 状态：已采纳
- 关联：`mini_agent/tools/file_tools.py:12-573`、`tests/test_tools.py:14-440`、提交 `fab83bd`

## 背景

baseline 的 `read_file` 先用 `readlines()` 读完整文件，再用 `cl100k_base` 和字符比例近似裁剪；`edit_file` 虽承诺唯一匹配，却调用无限次 `str.replace()`；`write_file` / `edit_file` 最后直接覆写目标文件（baseline `mini_agent/tools/file_tools.py:11-60,123-148,195-209,228-283`）。本轮复现了多处匹配被一起修改、CRLF 被改成 LF，以及近似 token 上限仍可超出的结果。

实现中还实际遇到两个提交边界：临时目录在 `os.replace()` 后清理失败，会出现“报告失败但文件已修改”；按事前快照清理新父目录，会在竞争下删除另一个进程刚创建的空目录。对应故障注入位于 `tests/test_tools.py:240-330`。

## 选项

1. **有界行窗口 + 唯一精确匹配 + 同目录原子替换**：行为容易解释和离线验证，但暂不处理读取后的并发变化。
2. **按 token 近似保留首尾 + 可选批量替换 + 直接覆写**：代码短，但截断位置、替换目标和失败后的磁盘状态都不可靠。
3. **模糊匹配或补丁格式 + 预览/恢复**：对模型生成内容更宽容、能表达多块修改，但需要更大的解析、权限和恢复边界。

## 决定

采用选项 1。`read_file` 使用 1-based 行窗口，编号正文最多 2000 个完整行或 50 KiB，并在未读完时给出下一次 `offset`；选中的超长行只读取到固定上限。这里的 50 KiB 是工具输出预算，不是 vendor token 结论（`mini_agent/tools/file_tools.py:12-14,214-387`）。

`edit_file` 把 LF/CRLF 视为同一种逻辑换行，但其余文本必须精确一致；零个、多个以及重叠的可能起点都在写入前失败，不提供批量替换开关（`mini_agent/tools/file_tools.py:174-203,468-573`）。写入和编辑在目标目录写临时文件，刷新文件内容后以 `os.replace()` 提交；提交前失败保持目标文件不变，已有文件保留 CRLF 约定和权限位（`mini_agent/tools/file_tools.py:52-126,390-573`）。

本决定不包含工作区访问边界、权限或沙箱、读取版本回执、并发覆盖检测、跨文件事务、检查点，也不承诺崩溃后的目录项持久性、所有者、ACL 或扩展属性不变。

## 为什么否决其他的

**否决选项 2**：代码编辑需要可继续的完整行和确定目标；token 估算既依赖不属于当前端点的编码，又不能保证最终结果真的落在上限内。批量替换还会把模型读取后新出现的匹配一起修改。若处理的是自然语言摘要，或者调用方同时提供并校验预期匹配数，保留首尾或批量替换反而可能更合适。

**否决选项 3**：Codex 的 `apply_patch` 和 Gemini CLI 的替换器会逐级放宽上下文匹配（源码证据见[文件工具调查](../reference/file-tools-survey.md)），这提高了成功率，也扩大了选错位置的空间。本项目还没有统一权限、预览、恢复和任务级错误修改指标，因此先选择能以唯一性证明目标的较小 contract。等多块修改成为可复现瓶颈，并能验证预览、恢复和错误修改率时，补丁格式反而是更合适的接口。

**没有把原子替换扩大成检查点**：同目录替换只保证单个目标在提交点前后可见，不恢复其他工具副作用或模型状态。只有跨文件和会话恢复能够逐字节验证时，检查点方案才值得进入实现。

## 怎么验证它是对的

定向测试：

```bash
.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_tools.py
```

实测结果为 `27 passed`。完整离线子集实测为 `120 passed`，命令见 `README.md`。

变异验证分别删除唯一匹配判断、`os.replace()` 和超长行早停，`test_edit_file_rejects_overlapping_match_positions`、`test_write_file_preserves_existing_crlf_and_permissions`、`test_read_file_does_not_consume_an_oversized_selected_line` 各自转红；恢复实现后定向测试重新全绿。

## 回头看

最初方案准备保留显式批量替换；审查指出它没有“预期匹配数”，无法发现读取后新增的匹配，因此实现阶段改为始终唯一。原子写入也从“临时目录 + 提交后清理”改成同目录临时文件，使 `os.replace()` 成为最后一个可能失败的提交步骤；父目录只记录本次实际创建成功的路径，避免失败清理删除竞争者创建的目录。

结果符合本轮目标，但并发文件覆盖仍未解决。后续只有在复现读取后文件变化造成的丢失更新时，才研究版本回执或其他并发控制，不把当前单文件原子替换描述成并发安全。
