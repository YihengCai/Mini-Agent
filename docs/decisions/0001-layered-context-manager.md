# ADR-0001：用三层上下文管理器替换现有文字摘要逻辑

- 日期：2026-08-24
- 状态：已被 ADR-0007 取代
- 关联：`docs/specs/01-context-manager.md` · `docs/PITFALLS.md` P-002 · ADR-0007

## 背景

`Agent._summarize_messages()`（`agent.py:153-232`）原地重建 `self.messages`；`_create_summary()`（`agent.py:235-292`）又会发送额外 LLM 请求。已确认三个问题：尚未结束的轮次进入摘要；旧摘要以 `role="user"` 再次参与压缩；未截断的工具结果在失败路径中原样写回，导致上下文变大。复现见 P-002。

## 选项

1. 三层派生视图：工具结果淘汰、单一摘要窗口、FileLedger。
2. vendor 提供的 `context_management`。
3. 只保留最近 K 条消息的滑动窗口。
4. 语义排序后淘汰。
5. 重新载入被淘汰的结果。

## 决定

当时选择选项 1：`raw_log` 仅追加，`build_view(raw_log, state)` 结果确定；工具调用组不可切分；只保留一份摘要；FileLedger 只记录路径、哈希和计数，不保存文件内容。该决定中的 FileLedger 边界后来由 ADR-0007 取代。

## 为什么否决其他的

vendor 提供的上下文管理只覆盖特定端点，也不能验证本项目自己的消息历史不变量。只有端点能力已经确认、项目不需要掌握压缩逻辑时，它才更合适。

固定 K 条消息的滑动窗口简单且结果确定，但 K 可能切入工具调用组，并丢失早期任务约束。任务很短、没有并行工具调用时，它更合适。

语义排序增加模型调用和不确定性。只有外部评测能证明排序优于按时间或大小淘汰，且有重新载入的降级方案时才值得做。

重新载入对长任务有价值，但不改变配对、边界或触发条件这些核心问题。需要频繁回看旧工具输出时再加。

## 怎么验证

- `tests/test_context_invariants.py`：随机消息历史中没有未配对记录和空内容，重复构建逐字节一致；
- `scripts/ctx_bench.py`：离线重放，比较请求 token 峰值与累计值；
- 模型服务缓存指标只在 C1–C3 探测通过后加入。

## 回头看

FileLedger 没有独立失败测试，且与编辑引擎的文件变化状态重复。ADR-0007 删除该层，保留仅追加的原始日志、工具结果淘汰与单一摘要窗口。
