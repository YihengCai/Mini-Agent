# 决策记录（ADR）

这个目录记的是**选择**，不是设计，也不是 bug。

规范文档分工固定，不要混：

| 目录 / 文件 | 回答的问题 |
|---|---|
| `docs/AGENT_ROADMAP_CN.md` | 现状是什么、哪里坏了（带 `file:line` 证据与确认级 bug） |
| `docs/BUILD_LIST_CN.md` | 先做什么、依赖什么 |
| `docs/mechanisms.md` | 每个机制的唯一状态 |
| `docs/specs/` | 某个模块**怎么造**（新建文件、函数签名、数据结构、要改哪些行） |
| `docs/decisions/`（本目录） | 为什么是这个方案而不是另一个，当时手里有什么证据，以及怎么证明选对了 |

一条 ADR 只有一个读者场景：半年后（或面试时）有人问"你为什么不用 X"。答案必须已经在文件里，带着当时的 `file:line` 和实测数字，而不是靠现场回忆。

## 编号规则

- 文件名 `NNNN-kebab-case-英文短语.md`，四位数，单调递增。`0000-template.md` 是模板，不是一条决策。
- 编号一旦发出就**不复用、不重排**。删掉一条 ADR 等于伪造历史。
- 状态取值只有四个：`已采纳（未实现）` / `已采纳（已实现）` / `已废弃` / `已被 ADR-NNNN 取代`。
- 改主意时**不改旧文的正文**：把旧文状态改成 `已被 ADR-NNNN 取代`，新开一条，并在新文的「关联」里反向指回旧编号。旧文里那个"当时以为对"的判断，正是最值钱的部分。
- 「回头看」一节在实现完成后回填：哪一条否决理由错了、哪个数字和预期差多少、代价比估的高还是低。这一节空着不算问题，写成"一切如预期"才是问题。

## 什么时候要新开一条 ADR

出现下面任意一条就写，不要攒：

1. **你在两个以上做法之间选了一个，而被否决的那个不是显然更差。** 判据很简单：如果你能想象一个称职的工程师选另一个，就得写下你为什么没选。
2. **决定改变了模块边界或数据流方向** —— 谁持有状态、谁调谁、闸门放在构造点还是分发点。例：`self.messages` 从"发出去的东西"变成"只追加的 raw log"（ADR-0001）；强制点放 `cli.py` 的构造处而不是 `agent.py:436` 的分发处（ADR-0003）。
3. **决定是「明确不做某件事」，而这件事在别处被当成标配。** PageRank repo map、tool 结果回填、完整 shell 文法 —— 不写下来，日后看起来就像忘了做，而不是想过之后砍掉的。
4. **理由是一个实测数字或一次踩坑，而这个数字/坑不写下来半年后会被当成随口定的。** 例：`min_steps_between_compactions=8` 来自缓存读写价格比推出的盈亏平衡；SBPL 语法错误退出码 `65`；`rg --files` 382 对 `rglob('*')` 7062。数字必须标注机器、日期、命令。
5. **顺序决定** —— 两件事都要做，但先后影响返工量。ADR-0002 整条就是这一类。

**不要为这些写 ADR**：单纯的 bug 修复、重命名、格式化、一处 `file:line` 的订正、规格里已经写清的实现细节。那些进 commit message 或直接改 `docs/specs/`。

## 硬规则

- **每一条关于代码的断言都要带 `file:line`，写的时候回代码核实一遍**（`sed -n` / `grep -n`）。核实不了就删掉这句话，不要软化成"似乎""大概"。
- **不许编数字。** 没实测过的写「待测」。实测过的标注机器 / 日期 / 命令，例：「本机 Darwin 25.5.0，2026-08-24，仓库 `953b943` 工作树」。
- 标识符、路径、`file:line`、API 字段名、命令、错误信息一律保留英文。
- 「为什么否决其他的」每一项都要写清**在什么条件下它反而是对的**。写不出这句，说明你还没真正理解那个方案，只是不喜欢它。
