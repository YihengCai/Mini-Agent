全表的重心是第三列「为什么错」：它必须给出可指认的失败模式，带 `file:line` 或 API 行为；写不出第三列的行不配上这张表，它只是一个 feature。

## 怎么维护

- **一个机制落地 = 一次表格更新 + 一条 ADR。** 同一个 PR 里改「状态」列、把「抓回归的测试」列的「待建」换成真实测试名（含 `::test_xxx`），并在 `docs/decisions/` 新建 `NNN-<机制>.md`，从状态列链过去。测试名还是「待建」就不许写「已落地」——那一列是这张表唯一的验收口。
- **实现细节不写在这里。** 数据结构、函数签名、要改哪些行属于 [`docs/specs/`](./specs/)，权衡与「为什么不是另一种做法」属于 ADR。这一页只回答六个问题，一行一遍。
- **第三列会过期。** 每一条 `file:line` 都锚在具体代码上；机制一落地，那段代码就没了。落地时把第三列改写成「原实现（`953b943` 的 `agent.py:186`）如何失败」的过去式，不要删——那正是这张表的价值所在。
- **数字只写实测。** 每个数字带上机器 / 日期 / 模型，且必须能被重跑。**已经有一次教训**：`rg --files` 在同一天内从 364 变成 391 —— 不是仓库漂移，是**我们自己往 `docs/` 里加文件**。所以凡是对工作树取样的计数，写清取样时刻，并优先给**比值**（rglob ÷ rg ≈ 18×）而不是绝对值。没跑过就写「待测」。
- **C 档三行不升级。** 它们停在「设计未实现」是主动划的边界，配套 `docs/limits.md` 说明为什么。要动它们，先改 [BUILD_LIST_CN.md](./BUILD_LIST_CN.md) 的分档理由。
