## 怎么填这张表

`scripts/provider_probe.py`（**待建**）：每项打印 `PASS / FAIL / N/A + 证据`，把结果写回本文件的「结果」「测于」两列。要求：

- 每项**独立**发请求，一项失败不影响其他项；
- 输出要带**原始证据**（usage 数值、错误码、错误信息原文），不要只给一个勾；
- 探测本身要最小化请求；运行前明确显示将执行哪些真实 API 调用；
- 结果里 `N/A` 和 `FAIL` 要区分：前者是"端点不支持"，后者是"支持但我的用法错了"。

## 能力缺失时的降级路径（设计里必须写）

| 能力 | 不可用时怎么办 |
|---|---|
| C1/C2/C3（缓存） | 缓存断点代码保留但空转；压缩的双阈值/滞回**不再由缓存成本推导**，改为纯上下文预算驱动；成本表只报 token 数不报缓存命中率，并写明本端点不支持 |
| C4/C5（流式） | 退回非流式 `generate()`；`stream_generate` 的默认实现已经是"整段返回再一次性发 delta"，渲染层不用改 |
| C6（并行工具） | 压缩的边界规则仍然要写（组是原子的），但属性测试改为**构造**并行组来覆盖，而不是依赖真实响应产生 |
| C7/C8（400 规则） | **这两项如果端点更宽容，不变量照样要守**——放宽的端点只是让 bug 更晚暴露，不是让 bug 消失。测试断言写在我们自己的 `assert_history_valid()` 上，不依赖端点报错 |
| C10（thinking） | 不回传 thinking，记一条 PITFALL 说明代价 |
| C12 | `token_limit` 落到配置里，用探测值而不是硬编码 80000 |
